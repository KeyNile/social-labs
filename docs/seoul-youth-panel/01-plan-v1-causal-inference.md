# social-labs 정책효과 시뮬레이션: NLSY97 → 서울청년패널 이식 구현 계획

> 대상 저장소: `github.com/KeyNile/social-labs` (Python 백엔드 + TypeScript 프론트엔드)
> 교체 데이터: `1-2차 서울청년패널 머지데이터(beta2)` — 6,515명 × 1,776변수, 1·2차 패널

---

## 1. 핵심 전략: "데이터 어댑터로 갈아끼우기"

NLSY97과 서울청년패널은 **둘 다 청년 추적 패널**이라는 점에서 시뮬레이션 골격(처치–결과–공변량 → 인과추정 → 정책 시나리오)은 그대로 재사용할 수 있습니다. 따라서 백엔드 전체를 다시 쓰는 대신, **데이터 진입 지점에 표준화 어댑터 레이어를 한 겹 끼워** NLSY97이 들어오던 자리에 서울청년패널을 흘려보내는 방식이 가장 빠르고 안전합니다.

NLSY97과 서울청년패널의 결정적 차이는 다음과 같으며, 이 차이가 어댑터에서 흡수해야 할 작업의 전부입니다.

| 항목 | NLSY97 (미국) | 서울청년패널 | 어댑터에서 할 일 |
|---|---|---|---|
| 단위/구조 | 연단위 다회차 long 패널 | 1차·2차 2시점, **wide 포맷** (`p01*`=1차, `p02*`=2차) | 2시점 wide → 분석용 long 변환 |
| 식별자 | PUBID | `PID` (6,515명) | ID 표준화 |
| 통화/소득 | USD, 연소득 | **만원 단위, 월평균** | 단위 정규화 |
| 가중치 | 패널 가중치 | `cross_w1/w2`(횡단), **`long_w2`(종단)** | 종단 가중치 연결 |
| 정책 변수 | 제도별 수급 플래그 | `k`-계열: 정책별 **인지·이용·이용의향**(2차는 만족도 추가) | 처치 변수 표준 매핑 |
| 결측 코딩 | 음수 reason 코드 | 한글 라벨('있다/없다', '취업/실업'…) + `NaN` | 라벨→수치 인코딩 |

핵심 산출물은 **`SeoulYouthPanelAdapter`** 하나입니다. 이 어댑터가 raw `.dta`를 받아, NLSY97 파이프라인이 기대하던 것과 동일한 "표준 분석 테이블(standardized analysis frame)"을 내보내면, 그 아래 인과추론·시뮬레이션·API 코드는 거의 손대지 않아도 됩니다.

## 2. 데이터 진단 결과 (이미 확인된 사실)

실제 `.dta`를 열어 확인한 내용입니다. 계획은 이 사실에 근거합니다.

- **표본**: 총 6,515행. 1차 본조사 참여 5,194명, 2차 본조사 5,083명(+위성 138, 군복무 44).
- **패널 분석 표본**: 종단 가중치 `long_w2`가 유효한 **약 3,762명**이 두 시점 연결 분석의 코어 표본.
- **명명 규칙**: `p01xxx`=1차, `p02xxx`=2차, `s02xxx`=2차 위성. 같은 문항은 접두사만 다른 쌍(`p01g10`↔`p02g10`)으로 존재 → **사전/사후 비교가 그대로 가능**.
- **처치(정책) 변수 `k`-계열**: 서울시·중앙정부의 청년정책 약 30종에 대해 각각 인지/이용/이용의향이 측정됨. 2차에는 **만족도**까지 추가. 예: `p01k26`(청년수당 이용) = `있다`/`없다`/`NaN`, 1차 이용 347명·2차 287명.
- **결과 변수**: 양 시점 공통으로 **개인 월총소득**(`p01g10`/`p02g10`), **가구 총소득**(`p01g11`/`p02g11`), **경제활동상태**(`p01eco`/`p02eco`: 취업/재학/실업/비재학미취업), **삶의 만족도**(`p01j8`/`p02j8`), **CES-D 우울 11문항**(`p01j51`~`p01j61` / `p02j51`~), 자존감·만족도 배터리 등 다수.
- **주의**: 소득(`g10`) 등 일부 수치형이 object/categorical로 로드됨 → ETL에서 `to_numeric` 강제 변환 필요. 결측은 비응답·해당없음이 섞여 있어 변수별 처리 규칙 필요.

## 3. 단계별 구현 로드맵

### Phase 0 — 저장소 파악 & 통합 지점 식별 (0.5일)
GitHub가 자동 브라우징을 막아 내부 파일까지는 외부에서 확인하지 못했습니다. 클론 후 가장 먼저 아래를 파악해 "어디에 어댑터를 끼울지"를 확정합니다.

```bash
git clone https://github.com/KeyNile/social-labs.git
# 데이터 진입 지점·시뮬레이션 엔진 찾기
grep -rin "nlsy\|pubid\|read_csv\|read_stata\|\.dat\b" backend/
# 인과추정 방식 확인 (DiD / 매칭 / 회귀 / ML 반사실)
grep -rin "did\|propensity\|psm\|matching\|treatment\|counterfactual\|effect" backend/
# API 계약 확인 (프론트가 기대하는 응답 스키마)
ls backend/ && cat backend/requirements.txt
sed -n '1,80p' docs/superpowers/*  # 설계 의도 문서
```
**산출**: ① 데이터 로더 모듈 경로, ② 시뮬레이션 엔진이 기대하는 입력 컬럼 스키마, ③ `/simulate`류 API의 요청/응답 JSON 스키마. 이 세 가지가 이후 단계의 인터페이스 계약이 됩니다.

### Phase 1 — ETL & 표준화 어댑터 (2~3일) ★최우선
`backend/data/seoul_youth/` 신설. `SeoulYouthPanelAdapter` 구현.

1. **로드**: `pandas.read_stata`로 `.dta` 적재(라벨 보존). 94MB이므로 필요한 컬럼만 선택 로드.
2. **wide→long 변환**: `PID` 기준으로 `p01*`/`p02*` 쌍을 `(PID, wave)` 2행 구조로 reshape. 매칭 안 되는 단일시점 문항은 별도 보관.
3. **타입/단위 정규화**: 소득류 `to_numeric`(만원 유지 또는 원 환산 택1, 상수로 고정), 한글 범주 라벨 → 코드 인코딩 사전화.
4. **가중치 연결**: 횡단 분석엔 `cross_w1/w2`, 패널(DiD)엔 `long_w2` 부착. 가중치 결측 행은 분석 표본에서 플래그 처리.
5. **표준 스키마 출력**: NLSY 파이프라인이 기대하던 컬럼명으로 매핑한 `analysis_frame` 반환(예: `id, wave, treat_<policy>, outcome_income, outcome_employed, outcome_lifesat, cov_*, weight`).

> 검증: reshape 후 `n_PID`가 6,515로 보존되는지, `long_w2` 유효 표본이 ~3,762로 재현되는지 단위테스트.

### Phase 2 — 변수 매핑 정의 (1~2일)
코드가 아닌 **설정(config)** 로 분리해 정책·결과를 자유롭게 갈아끼우게 만듭니다. `backend/config/seoul_mapping.yaml` 예:

```yaml
policies:
  youth_allowance:           # 청년수당
    label: "서울시 청년수당"
    treat_use:    {w1: p01k26, w2: p02k26}   # 이용 여부 = 처치
    treat_aware:  {w1: p01k11, w2: p02k11}   # 인지(스필오버 통제용)
    intent:       {w1: p01k41, w2: p02k41}
  youth_rent_support:        # 청년월세지원
    treat_use:    {w1: p01k24, w2: p02k24}
  mind_health:               # 서울시 마음건강 지원
    treat_use:    {w1: p01k28, w2: p02k28}
  hope2x_account:            # 희망두배 청년통장(2차 신규)
    treat_use:    {w2: p02k2q7}
outcomes:
  income_personal:  {w1: p01g10, w2: p02g10, type: numeric}   # 개인 월총소득
  employed:         {w1: p01eco, w2: p02eco, type: cat→binary(취업=1)}
  life_satisfaction:{w1: p01j8,  w2: p02j8,  type: ordinal}
  depression_cesd:  {w1: [p01j51..p01j61], w2: [p02j51..], type: scale_sum}
covariates: [sex, birth_y, region01, p01edu, p01htype, p01g11(baseline_hh_income), ...]
```

### Phase 3 — 인과추론/시뮬레이션 엔진 (3~5일)
2시점 패널이므로 NLSY 엔진의 추정 방식에 맞춰 **다음 중 저장소가 쓰던 것**을 우선 채택하되, 데이터 구조상 아래가 자연스럽습니다.

- **이중차분(DiD)**: 1차→2차 변화량을 정책 이용군 vs 미이용군 비교. 패널의 가장 직관적 정책효과.
- **성향점수매칭/IPW**: 1차 공변량으로 이용 성향을 보정 후 2차 결과 비교(자기선택 편의 완화). `long_w2` 가중과 결합.
- **(엔진이 ML 반사실 방식이면)** 처치=정책이용, 라벨=결과변화로 동일 학습 인터페이스에 주입.

**시뮬레이션 레이어**: 추정된 처치효과를 받아 "정책 수혜 확대/축소" 시나리오를 모의. 예) 청년수당 이용률을 X%p 올렸을 때 표본 평균 소득·취업률·삶의만족도 기대 변화 → 가중 집계로 모집단 추정.

### Phase 4 — 백엔드 API 연결 (1~2일)
Phase 0에서 확인한 API 계약을 유지한 채 내부만 교체. 정책 목록·결과 지표를 서울 데이터 기준으로 노출하고, 응답 JSON 스키마는 프론트가 깨지지 않도록 동일 형태 유지(필드명만 매핑).

### Phase 5 — 프론트엔드 현지화 (1~2일)
정책 선택지(청년수당·청년월세지원·마음건강·희망두배통장…), 결과 지표 라벨, 통화 단위(만원/₩), 한국어 UI 텍스트 교체. 차트 축·툴팁 단위 점검.

### Phase 6 — 검증 & 문서화 (2일)
- **재현 검증**: 알려진 기술통계(이용률·평균소득)와 일치하는지.
- **가중 vs 비가중** 결과 비교, 민감도 분석(처치 정의를 '이용'→'이용+인지'로 바꿔보기).
- **한계 명시**(아래 §5).

## 4. 권장 1차 타깃 정책 (구현 난이도·표본 고려)

양 웨이브에 모두 있고 이용 표본이 충분해 **DiD가 바로 되는** 정책부터 시작하길 권합니다.

| 정책 | 처치(이용) 변수 | 핵심 결과 | 비고 |
|---|---|---|---|
| 청년수당 | `p01k26`/`p02k26` | 소득·취업·삶의만족·우울 | 이용 347/287, 가장 안정적 |
| 청년월세지원 | `p01k24`/`p02k24` | 주거비·주거만족·소득여력 | 주거 결과변수와 직결 |
| 서울시 마음건강 지원 | `p01k28`/`p02k28` | CES-D 우울·삶의만족 | 심리 결과에 특화 |
| 국민취업지원제도 | `p01k53`/`p02k53` | 취업·소득 | 중앙정부 대조군 |
| 희망두배 청년통장 | `p02k2q7` (2차 신규) | 자산형성·저축 | 2차 단면 분석부터 |

## 5. 리스크 & 주의사항

- **2시점뿐**: NLSY97 같은 다회차가 아니므로 시계열 추세·동적 효과는 제한적. DiD의 평행추세 가정 검증이 1시점차로는 어렵다는 점을 명시.
- **자기선택**: 정책 '이용'은 무작위 배정이 아님 → 매칭/IPW로 보정하되 잔존 편의 가능성 고지(실험이 아닌 관찰자료 시뮬레이션임을 UI에 표기).
- **결측 구조**: `NaN`이 비응답·해당없음·미인지 등 여러 의미를 섞음. 처치 정의 시 "미이용(없다)"과 "결측"을 구분.
- **소액·소표본 정책**: 이용자 수십 명대 정책은 추정 불안정 → 신뢰구간을 반드시 표기하거나 제외.
- **가중치 일관성**: 횡단/종단 가중치를 분석 설계에 맞게 선택(패널효과엔 `long_w2`).

### 요약
NLSY97 자리에 **`SeoulYouthPanelAdapter` 한 겹**을 끼워 표준 분석 테이블을 공급하면, 그 위의 인과추론·시뮬레이션·API·프론트는 최소 수정으로 재사용됩니다. 데이터는 이미 **정책별 이용 여부(처치) × 사전/사후 결과 × 종단 가중치**가 갖춰져 있어, **DiD/매칭 기반 정책효과 시뮬레이션에 즉시 적합**합니다. Phase 1(ETL 어댑터)이 전체의 성패를 좌우하는 최우선 작업입니다.
